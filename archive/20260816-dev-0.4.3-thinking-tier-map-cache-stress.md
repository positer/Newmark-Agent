日期：2026-08-16

## 背景

`thinking_tier_map` 上线后，需要验证新情况下（模型配置原生档位映射、请求体携带
映射后的 `reasoning_effort`）缓存命中是否稳定：
1. 映射解析是否确定（同档位反复请求 → 同值，无状态泄漏 / 无随机漂移）；
2. 映射档位是否只进请求体顶层字段、绝不泄漏进 system prompt（不破坏前缀缓存）；
3. Agent 全链路（intelligence → intelligenceConfig → chatStreamWithTools →
   reasoningEffort）下缓存命中率统计是否正确且不漂移；
4. 档位切换（含 ultra 归一）是否按精确 / 降级 / 最低档规则稳定生效。

## 套件：DESKTOP/src/tests/thinkingTierMapCacheStressVerify.ts（67 断言）

全部走真实 provider 序列化路径（V2 adapter + 本地 HTTP capture server，
`chatStreamWithTools` → `/chat/completions` SSE），不使用 fake provider 直出 token。

### Part A：映射确定性 + 缓存前缀稳定（真实序列化）

- 模型 `tier-map-model` 配置 `thinking_tier_map: { minimal: 'low', balanced: 'medium', deep: 'high' }`；
- 同一 system 前缀 × 30 轮请求（tier=max）：
  - 30/30 请求体 `reasoning_effort === 'deep'`（max → 就近降级到 high 的原生档位）；
  - 30/30 system 内容字节级一致（`new Set(systems).size === 1`）；
  - 映射档位绝不进入 system prompt（前缀缓存不被映射破坏）。

### Part B：多档位切换压力（6 档 × 10 轮 = 60 请求）

| Newmark 档位 | 期望原生档位 | 规则 |
|---|---|---|
| low | minimal | 目标低于全部已映射档位 → 取最低档 |
| medium | balanced | 精确命中 |
| high | deep | 精确命中 |
| xhigh | deep | 就近降级 |
| max | deep | 就近降级 |
| ultra | deep | ultra 归一为 max 后降级 |

每档 10 轮请求 `reasoning_effort` 全部一致（`new Set(...).size === 1`）。

### Part C：Agent 集成压力（5 Build × 8 tool 子轮 = 45 请求）

- 真实 `Agent` + `forcedProvider = LLMProvider(..., thinkingTierMaps)`；
- C1 默认档位 medium（2 Build）：18 请求全部 `balanced`（精确命中）；
- C2 `setIntelligence('ultra')`（3 Build）：27 请求全部 `deep`（归一 + 降级）；
- 每个 Build 首请求含 `## Build Context Bootstrap`，其后 8 个 tool 子轮共享
  字节级一致的 system 前缀，映射档位不进缓存前缀；
- 模拟 usage（input 1000 / cached 950 / output 40 / 请求）：
  `contextWindow()` 全对话 token、cache-read token、缓存命中率与模拟值完全一致，
  命中率 0.95 ≥ 0.9 保持高位。
