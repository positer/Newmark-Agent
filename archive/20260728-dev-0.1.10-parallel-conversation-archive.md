# dev-0.1.10 Low-Latency Parallel Conversation Lifecycle

Date: 2026-07-28
Scope: conversation creation and archive throughput under rapid consecutive input

## Reported failure

Rapidly clicking archive on several conversation rows could lose intended operations. The first repair introduced a 220 ms quiet window and waited for every request in the burst before committing UI changes. That protected click targets but created a visible latency regression for every new/archive interaction and still did not provide true backend parallelism.

The deeper causes were:

- the renderer placed a batch-settlement barrier on the critical interaction path;
- the Electron Utility and WSL runtime pools awaited slow process shutdown while holding their shared capacity serialization lock;
- archive cleanup deleted every conversation with an equal content signature, so separately created empty conversations could be removed together;
- new-conversation activation painted its returned snapshot and then performed a redundant state read that could cold-start the runtime;
- millisecond-only conversation IDs could collide during a rapid creation burst.

## Implementation

- Advanced `DESKTOP/package.json` and `DESKTOP/package-lock.json` to `0.1.10`.
- Removed the 220 ms quiet window, batch-settlement barrier, and pending-row rendering from `DESKTOP/src/ui/index.html`.
- Archive clicks now capture a stable row ID, remove that exact row synchronously, switch the active row locally when needed, and dispatch `api.archive(...)` without awaiting any other target.
- Each target retains its own rollback snapshot and the shared pre-burst ordering. A negative receipt or exception restores only that row in original order; successful calls schedule only a 40 ms coalesced background archive-list refresh.
- When active rows are removed rapidly, replacement activation is zero-delay coalesced and loads only the final active conversation after the immediate paints. A failed active archive restores the prior chat DOM immediately.
- New conversations use a monotonic per-renderer suffix in addition to the timestamp and paint the activation snapshot directly without a second `getState`.
- `agent.ts` deletes only the exact conversation state key requested; it no longer deletes equal-content duplicates.
- Electron Utility and WSL runtime pools mark an entry as disposing under the shared capacity lock, release the lock, and then await process shutdown. Different conversation runtimes can therefore stop concurrently.
- Added `DESKTOP/src/tests/conversationArchiveConcurrencyVerify.ts` and registered it in the normal test chain plus the focused `test:conversation-archive-concurrency` command.
- Extended `DESKTOP/src/tests/runtimePoolCapacityVerify.ts` with delayed-stop overlap measurements for both runtime pools.
